# PrismaPg transaction query serialization

The installed Prisma7.9.1 interpreter can dispatch sibling relation queries concurrently through one transaction connection. With pg8.23.0 this emits its query-queue deprecation warning. A local disposable trace on17October2026 reproduced it in the standalone public showcase read: Client.query -> PgTransaction.performIO/queryRaw -> query-interpreter relation Array.map. Successful HTTP responses do not make that warning absent or prove future-major compatibility.

`shared/serialized-pg.ts` wraps the public adapter factory/transaction interfaces used by API and worker database creation. Each transaction has its own FIFO for queryRaw, executeRaw, savepoint methods and terminal commit/rollback. Ordinary pooled queries and separate transactions remain independent. SQL, snapshot isolation, RLS context, DTO mapping, error conversion and pg/Prisma versions are unchanged. No warning is filtered, no pipeline option enabled, and installed dependencies are not patched.

Methods retain the original receiver, including stock private fields. Stock savepoint methods and a UDT parser using the supplied original queryable can perform an awaited nested call inside the current queue slot. A custom parser that closes over and re-enters the proxy is not supported; none is currently configured. Keep this limitation when extending adapter configuration.

The private scheduling tail recovers after query rejection so rollback can run, but callers receive the original failure. A terminal request closes admission immediately, drains already admitted operations, then invokes the original terminal method. Later queries and duplicate terminal calls are rejected to avoid use-after-release. Stock Prisma still sends COMMIT/ROLLBACK SQL before its terminal connection-release call; the wrapper does not invent successful transaction outcomes.

Unit tests exercise FIFO, original receivers/metadata, errors, savepoints, nested parser behavior, terminal ordering and retained pool concurrency. Actual disposable database tests, failure/timeout/visibility checks, source consistency and exact cleanup are separate required evidence; pure tests are not a substitute. Do not remove the wrapper solely because an upstream issue was closed: verify the installed released adapter and the actual regression before changing this policy. This is local compatibility handling, not a claim that Prisma/pg upstream or production deployment is fixed.
